# المرحلة الثالثة — تصميم المعمارية

الحالة: **مسودة للمراجعة**. لا شيء في هذه الوثيقة منفَّذ بعد، إلا ما ذُكر صراحةً أنه موجود في الكود الحالي.

المرجع: نتائج جرد الوظائف (المرحلتان 1 و2) على نسخة معزولة من قاعدة الإنتاج بتاريخ 2026-11-15.

---

## 1. المبادئ الحاكمة

1. **مصدر حقيقة واحد.** كل تقرير (أسبوعي، فتري، نهائي) يُبنى على الخادم من سجلات المستخدم، ولا يعيش في `localStorage` ولا في الكود.
2. **لا كتابة فوق نص المستخدم.** أي ناتج من الذكاء الاصطناعي يُحفظ كـ«اقتراح» ولا يصير محتوى إلا بقبول صريح.
3. **كل جملة لها مصدر.** الفقرة المولَّدة تحمل معرّفات الإدخالات التي بُنيت عليها. ما لا مصدر له يُرفض أو يتحول إلى سؤال توضيحي.
4. **المقاس غير المولَّد.** الإحصاءات تُحسب من السجلات وتُعلَّم `measured`. التحليل النوعي يُعلَّم `ai`. لا يختلطان في العرض.
5. **إضافة لا استبدال في القاعدة.** الجداول العشرة الحالية ومعرّفاتها لا تتغير. كل جديد جداول إضافية عبر ترحيلات Prisma بعد خط الأساس.
6. **لا ميزة ظاهرة لا تعمل.** الزر الذي لا يملك مساراً مختبَراً لا يُعرض.

## 3. نموذج التقرير الموحّد (Canonical Report)

يُعرَّف في `shared` ويستهلكه كل مُخرِج. يُبنى بدالة واحدة:

```ts
buildCanonicalReport(userId, { kind, range, lang, templateId }): CanonicalReport
```

```ts
interface CanonicalReport {
  meta: { id; kind: 'weekly' | 'periodic' | 'final'; lang: 'ar' | 'en';
          templateId; generatedAt; status; version };
  student: { name; academicId; department };
  institution: { name; unit; logoRef? };
  organization: { name; department?; address?; logoRef? };
  supervision: { academicSupervisor?; fieldSupervisor?; approval? };
  period: { start; end; weeks: number; plannedHours: number };
  facts: Fact[];            // إحصاءات مقاسة فقط
  sections: Section[];      // بالترتيب، حسب قالب الجامعة
  evidence: EvidenceRef[];  // صور بمعرّفاتها، لا Base64 داخل النموذج
  references: Reference[];
  appendices: Section[];
  issues: ValidationIssue[]; // نواقص وتحذيرات تُعرض للمستخدم
}

interface Section {
  key: SectionKey;          // intro | orgOverview | objectives | ...
  title: string;
  required: boolean;        // حسب القالب
  blocks: Block[];
}

type Block =
  | { type: 'paragraph'; text: string; provenance: Provenance }
  | { type: 'list'; ordered: boolean; items: string[]; provenance: Provenance }
  | { type: 'table'; caption?: string; columns: string[]; rows: string[][]; provenance: Provenance }
  | { type: 'figure'; evidenceId: number; caption: string }
  | { type: 'chart'; spec: ChartSpec; factKeys: string[] }   // بياناته من facts فقط
  | { type: 'heading'; level: 2 | 3; text: string };

interface Provenance {
  origin: 'user' | 'computed' | 'ai-accepted';
  sourceEntryIds: number[];   // فارغة فقط للنص الذي كتبه المستخدم مباشرة
  suggestionId?: number;      // إن كان أصله اقتراحاً مقبولاً
}

interface Fact {
  key: string;                // totalHours | daysLogged | categoryShare:...
  value: number | string;
  unit?: string;
  kind: 'measured';
  sourceEntryIds: number[];
}
```

**هيكل الأقسام قابل للضبط.** القالب يحدد أي الأقسام الـ23 مطلوب وترتيبها. القسم الفارغ غير المطلوب يُحذف من المخرجات؛ الفارغ المطلوب يظهر في `issues` ولا يُملأ بحشو.

### المرحلة الأولى من النموذج لا تحتاج تغييراً في القاعدة

`buildFinalReportData` الحالية تجمع البيانات نفسها من `entries` و`report_profile` و`weekly_evidence`. تُعاد كتابتها لتُخرج `CanonicalReport`، وتبقى الدالة القديمة كغلاف توافق للمسارات الحالية.

### جداول إضافية (تحتاج موافقة قبل الترحيل)

| الجدول | الغرض |
|---|---|
| `report_documents` | تقرير محفوظ: النوع، المدى الزمني، اللغة، القالب، الحالة، حذف ناعم |
| `report_sections` | محتوى كل قسم كـJSON من `Block[]` |
| `report_section_revisions` | نسخة عند كل حفظ أو قبول اقتراح |
| `ai_suggestions` | الأصل، المقترح، المزوّد، النموذج، التقييم، الحالة: `pending/accepted/rejected` |
| `export_jobs` | بديل الطابور الذي في الذاكرة |

الجداول الحالية لا تُمسّ. `report_profile` يبقى مصدر بيانات الغلاف والنصوص الأربعة الحالية، ويُقرأ منه عند غياب قسم في `report_sections`.

### التقارير الفترية

الوضع الحالي: محتوى ثابت في `periodicP2Templates.ts` و`PeriodicTab.tsx` يخص متدرباً واحداً، ومسودات في `localStorage`.

المستهدف: تقرير فتري = `report_documents` بمدى زمني يختاره المستخدم، يُجمَّع من أسابيعه. المسودات المحلية الموجودة تُرفع مرة واحدة إلى حساب صاحبها عند أول فتح، ولا تُحذف من المتصفح قبل تأكيد الرفع.

**قرار مطلوب:** المحتوى الثابت الحالي هو تقرير حقيقي لصاحب المشروع. المقترح نقله كبيانات إلى حسابه (تقريران محفوظان) وإزالته من الكود، لا حذفه.

## 4. طبقة الذكاء الاصطناعي

### 4.1 تجريد المزوّدين

```ts
interface LlmProvider {
  id: 'anthropic' | 'openai' | 'gemini' | 'groq';
  health(): Promise<{ ok: boolean; reason?: string; checkedAt: Date }>;
  generate(req: {
    system: string; messages: Msg[]; jsonSchema?: object;
    maxOutputTokens: number; temperature: number; signal: AbortSignal;
  }): Promise<{ text: string; usage: { inputTokens; outputTokens };
                model: string; latencyMs: number }>;
  stream?(req): AsyncIterable<string>;
}
```

- المفاتيح على الخادم فقط. معرّفات النماذج في الإعدادات لا في الكود، وتُتحقق عند الإقلاع من واجهة سرد النماذج لكل مزوّد.
- مهلة لكل طلب، إعادة محاولة واحدة على أخطاء الشبكة و429 و5xx فقط، ثم الانتقال للمزوّد التالي في ترتيب مضبوط.
- الاستهلاك يُسجَّل من أرقام المزوّد الفعلية، لا من طول النص كما هو الآن.
- البث حقيقي من المزوّد، لا تقطيع لنتيجة جاهزة كما في `routes/ai.ts` اليوم.
- مؤشر توفر في الواجهة مبني على `health()`؛ وجود مفتاح لا يعني أن المزوّد يعمل.

**غير مُتحقَّق منه:** معرّفات النماذج الحالية وتوافق واجهات المزوّدين الأربعة. يُتحقق منها في المرحلة الخامسة مقابل التوثيق الرسمي وبمفاتيح حقيقية قبل أي ادعاء بالعمل.

**قرار مطلوب:** الواجهة اليوم تخزّن مفتاح Gemini الخاص بالمستخدم في `localStorage` وترسله مع كل طلب. المقترح إلغاء ذلك والاكتفاء بمفاتيح الخادم.

### 4.2 مصير المحرك البديل

المحرك النصي الحالي (`aiService.ts` من السطر 430 تقريباً) يُسحب من كل مسار يُسمّى ذكاءً اصطناعياً:

- لا «تنقيح» ولا «تدقيق» ولا «ملخص» بقواعد نصية.
- لا ترجمة عبر واجهات Google غير الرسمية أو MyMemory.
- عند غياب مزوّد يعمل: رسالة صريحة «الخدمة غير متاحة الآن» مع السبب، لا ناتج مقلَّد.

يبقى منه ما هو حتمي فقط: حساب الساعات، التجميع الأسبوعي، استخراج الاختصارات المذكورة حرفياً.

### 4.3 مسارات العمل المتخصصة

مسارات لا «وكلاء مستقلون»: كل مسار قالب تعليمات + مخطط مخرجات + قواعد إسناد، فوق البنية المشتركة.

| المسار | المدخل | عقد المخرجات |
|---|---|---|
| الكتابة الأكاديمية | إدخالات محددة + سياق القسم | `{ text, usedEntryIds[], missing[] }` |
| التحرير | نص واحد | `{ text, changes[] }` دون تغيير في المعنى |
| البنية | هيكل التقرير وأطوال أقسامه | `{ issues[] }` بلا توليد نص |
| الكتابة التقنية | إدخال + مصطلحاته | `{ text, termsKept[] }` |
| التقييم | الأصل والمقترح | `{ grounded, unsupportedClaims[], repetition, verdict }` |
| الترجمة | قسم ببنيته | البنية نفسها بلغة أخرى، مع قائمة المصطلحات المثبتة |

أوضاع المستخدم الثلاثة عشر (إعادة صياغة، توسيع بسياق، توضيح، …) تُربط بهذه المسارات الستة؛ لا مسار لكل زر.

### 4.4 خط الإنتاج لكل عملية

```
1. جمع السياق الأدنى   الإدخالات المعنية + القسم + مسرد المصطلحات
2. التوليد              بمخطط JSON مُلزِم
3. فحص حتمي             أرقام أو أدوات أو اختصارات ليست في المصدر → رفض
4. تقييم بنموذج          إسناد كل ادعاء إلى إدخال
5. حفظ كاقتراح          ai_suggestions (pending)
6. عرض الفرق            قبول · رفض · تعديل يدوي
7. عند القبول           نسخة جديدة في revisions ثم الكتابة
```

الخطوة 3 هي التي كانت ستمنع ما حدث في الجرد: عنوان «Switch Port Administration» لملاحظة لا تذكر المنافذ، واستبدال `ont` داخل `continue`.

**عند نقص المعلومات:** المخرج `missing[]` أسئلة محددة للمستخدم («ما الأدوات التي استخدمتها في الفحص؟») بدل اختلاق إجراءات.

**حدّ الادعاء:** ناتج مسار التقييم يُعرض كـ«فحص آلي»، لا كتحقق أكاديمي مستقل.

### 4.5 الخصوصية

يُرسل للمزوّد النص المطلوب معالجته وسياقه المباشر فقط. لا اسم المتدرب، ولا رقمه، ولا الصور، ولا بقية السجل.

## 5. محرك النشر

كل مُخرِج يأخذ `CanonicalReport` ويُنتج ملفه باستقلال. لا مُخرِج يعتمد على ناتج آخر.

| الصيغة | التقنية | ما يبقى من الحالي | ما يتغير |
|---|---|---|---|
| DOCX | مكتبة `docx` (الحالية) | الأنماط، الترويسة والتذييل، الروابط الداخلية | فهرس Word حقيقي يتحدث تلقائياً؛ جداول للبيانات فقط؛ تحويل الصور إلى PNG قبل التضمين |
| PDF | Chromium بلا واجهة مع قالب طباعة مخصص | لا شيء (اليوم طباعة المتصفح) | نص متجه بخطوط مضمَّنة، ترقيم، ترويسات، فهرس بأرقام الصفحات |
| PPTX | `pptxgenjs` (الحالية) | الرسم البياني وملاحظات المتحدث | مخطِّط شرائح: فكرة واحدة وحدّ أقصى للكلمات لكل شريحة، RTL، خط عربي، صور، عدد شرائح حسب المحتوى |
| HTML | قالب مستقل بملف واحد | الفهرس بالروابط | بحث، طيّ الأقسام، سمة فاتحة وداكنة، خطوط مضمَّنة، رسوم SVG، بلا أي طلب خارجي |
| Markdown | مُخرِج نصي | ترتيب الفصول | جداول، مراجع، روابط صور |

**لماذا Chromium للـPDF:** تشكيل الحروف العربية وRTL فيه صحيح دون معالجة خاصة، وهذا أضعف نقاط مكتبات PDF المباشرة. الناتج نص متجه لا لقطة شاشة.

**خطر يحتاج تحققاً:** تشغيل Chromium داخل حاوية Nixpacks على CranL غير مُختبَر (الحجم والذاكرة). إن تعذّر، البديل خدمة تصدير منفصلة. يُحسم بتجربة في المرحلة السابعة قبل الالتزام.

**خلل قائم يُصلَح هنا:** الصور تُضمَّن في DOCX ببيانات WebP باسم `.png`. PPTX لا يضمّن أي صورة.

### فحص جودة المستندات

فاحص لكل صيغة يعمل ضمن الاختبارات على تقارير نموذجية ثابتة:

- **DOCX:** وجود حقل الفهرس، الأنماط، RTL، صور بصيغة مدعومة، لا قسم فارغ.
- **PPTX:** حدّ الأحرف لكل شريحة، خاصية RTL، وجود الوسائط، لا تجاوز لحدود الشريحة.
- **PDF:** عدد الصفحات، الخطوط مضمَّنة، النص قابل للاستخراج، لا صفحة فارغة.
- **HTML:** صحة البنية، لا رابط خارجي، كل مرساة في الفهرس لها هدف.
- **Markdown:** تسلسل العناوين، صحة الجداول.

## 6. الرؤى من البيانات

كلها محسوبة من السجلات وتدخل النموذج كـ`facts`:

- أيام موثقة، ساعات فعلية مقابل المخطط، نسبة الإنجاز.
- توزيع النشاط حسب التصنيف، واتجاهه أسبوعاً بأسبوع.
- أسابيع بلا توثيق وفجوات الأيام.
- تغطية الأدلة: أسابيع لها صور مقابل أسابيع بلا صور.
- مقارنة بين فترتين: تغير التوزيع والساعات.
- المصطلحات والأدوات المذكورة حرفياً وتكرارها.

بيانات موجودة اليوم وغير مستغلة: `entry_revisions` (حجم التحرير)، `report_status_history` (زمن دورة المراجعة)، `ai_usage_logs` (الاستهلاك لكل مستخدم)، `report_section_comments` (لا واجهة لها).

التحقق من المدخلات يُشدَّد أولاً، لأن الإحصاءات تعتمد عليه: اليوم يُقبل تاريخ مثل `2026-13-45` ووقت نهاية قبل البداية.

## 7. معمارية الواجهة

### المسارات

```
/log                 التسجيل اليومي
/weeks/:n            مساحة الأسبوع
/periods/:id         مساحة التقرير الفتري
/report              مساحة التقرير النهائي
/export              مركز التصدير
/review              بوابة المشرف
/verify/:id/:hash    التحقق العام (موجود)
```

توجيه حقيقي بتحميل كسول لكل مسار، بدل التبويبات اليدوية في `App.tsx`.

### مساحة التقرير النهائي

ثلاثة أعمدة على الشاشات الواسعة، وتتحول لتبويبات على الجوال:

1. **الهيكل:** الأقسام بحالتها (مكتمل، ناقص، فيه تحذير) ومؤشر الاكتمال.
2. **المحرر:** القسم الحالي ككتل، مع شريط مصادر يبيّن الإدخالات التي بُنيت عليها كل فقرة.
3. **المساعد:** الاقتراحات المعلّقة بعرض الفرق، والأسئلة التوضيحية، وتحذيرات الفحص.

المعاينة الحية وسجل النسخ يُفتحان كلوحة جانبية، لا كصفحة أخرى.

### مركز التصدير

بطاقة لكل صيغة: الغرض، اللغة، القالب، حالة التوليد، التنزيل. يعتمد على `export_jobs`. الصيغة التي لم تجتز فاحصها لا تُعرض.

### الاتجاه البصري

هوية «دار نشر أكاديمية»، لا لوحة تحكم:

- الإبقاء على العنابي والخلفية الورقية الحاليين كمتغيرات، وإزالة 413 لوناً مباشراً من Tailwind تتجاوزها.
- حدّ أدنى لحجم الخط 13px (اليوم 387 موضعاً بـ11.5px أو أقل).
- خط واجهة وخط متن للتقرير نفسه، يُختاران بتجربة فعلية على نص عربي طويل.
- أيقونات `lucide-react` فقط، وقاعدة فحص في CI ترفض أي رمز تعبيري في الكود.
- مكوّنات Radix للحوارات والقوائم بدل `alert` و`confirm`.
- حركة برموز مدد موحدة، مع احترام `prefers-reduced-motion`.
- كل زر أيقوني له اسم مقروء.

## 9. ترتيب التنفيذ

1. **أساس الأمان (قبل أي ميزة):** خط الأساس وإيقاف `db push`، الثغرات الخمس، إيقاف الكتابة المباشرة فوق الإدخالات.
2. **أساس الجودة:** اختبارات API للصلاحيات والتصدير، بيانات نموذجية ثابتة، CI.
3. **النموذج الموحّد** دون تغيير في القاعدة، والمُخرِجات الحالية فوقه.
4. **طبقة الذكاء الاصطناعي** والاقتراحات (أول ترحيل إضافي).
5. **المُخرِجات الخمسة** وفاحصاتها.
6. **الواجهة** فوق ما سبق.

## 10. قرارات تحتاج صاحب المشروع

1. نقل محتوى التقارير الفترية الثابت إلى حسابه كبيانات وإزالته من الكود.
2. إلغاء مفتاح Gemini الذي يخزّنه المستخدم في المتصفح.
3. الجداول الإضافية الخمسة (كل ترحيل يُعرض منفرداً قبل تطبيقه).
4. Chromium للـPDF، بشرط نجاح تجربته على CranL.
5. تقييد التسجيل كمشرف (رمز دعوة أو موافقة).
6. أي مزوّدين تتوفر لهم مفاتيح فعلاً؛ من لا مفتاح له لا يُعرض في الواجهة.
